> **최종 Match Rate**: 98% (Act 1회 + 실파일 검증 1회)

## Executive Summary

### 1.1 개요

| 항목 | 내용 |
|------|------|
| 기간 | 2026-10-08 ~ 2026-10-10 |
| 범위 | 백엔드 파서 패키지 + KB 업로드·doc_chunk 연결 + 프론트 업로드 창 |
| 설계안 | C안 (infra 패키지에 리더 2개 + 어댑터, 도메인은 상수·예외만) |

### 1.2 결과 요약

| 지표 | 값 |
|------|----|
| Match Rate | 89% → 96% (Act-1) → **98%** (실파일 검증) |
| 신규 테스트 | 한글 파서 75개 + KB 통합 2개 + doc_chunk 2개 + 도메인·라우팅·프론트 |
| 실파일 검증 | 공개 저장소 실제 한글 파일 19개 (로컬), 그중 허용 라이선스 3개는 픽스처로 커밋 |
| 신규 모듈 커버리지 | 93% 이상 |
| 회귀 | **0건** (전체 53 failed = 변경 전 기존 실패 목록과 동일) |
| 신규 런타임 의존성 | `olefile` 1개 (BSD) |

### 1.3 전달한 가치

| 관점 | 결과 |
|------|------|
| **Problem** | KB 업로드가 pdf/xlsx/xls만 받아 한글 문서는 PDF로 변환해야 했다 |
| **Solution** | 순수 Python 리더 2개(HWP 5.0: olefile+zlib 레코드 파싱, HWPX: zipfile+XML)를 기존 확장자 라우팅에 추가형으로 연결 |
| **Function/UX Effect** | KB 업로드 창과 `/doc-chunk`에서 .hwp/.hwpx를 바로 올린다. 본문·표(셀 ` \| `, 행 줄바꿈)·표 캡션·글상자를 추출하고 머리말·꼬리말·각주·미주는 뺀다. 암호·배포용 문서는 422로 거부. 실제 한글 파일 19개에서 제어 문자 잔여물 0 |
| **Core Value** | 운영자(P2)가 원본 포맷 그대로 지식을 넣는다. 특정 도메인 하드코딩 없는 포맷 일반화 |

## 6. 회고

### 6.1 잘된 점

- kb-excel-upload의 확장자 라우팅 구조 덕에 추가형으로만 붙었다. 기존 테스트 수정 0줄
- 기준 실패 목록 diff로 회귀를 증명해 숫자 착시가 없었다
- 한글 프로그램이 없어도 공개 파서 프로젝트의 테스트 픽스처로 실파일 검증을 끝냈다. 행 오프셋을 원시 바이트로 확정했다
- 합성 바이트 테스트가 우연히 통과하던 캡션 케이스를 실파일 바이트로 바꿔 진짜 결함을 드러냈다

### 6.2 아쉬운 점

- 샘플 확보 방법을 Plan에서 정하지 않아 Do 내내 행 오프셋이 추정값이었다
- 캡션 결함은 합성 테스트만으로는 잡히지 않았다 (실파일 검증이 늦었다)
- 최초 설계 문서를 영어로 써서 다시 작성했다
- 셸 heredoc으로 한글·이스케이프·NUL이 섞인 파일을 고치다 여러 번 깨졌다 (Edit 도구·스크립트 파일로 복구)

### 6.3 다음에 해볼 것

- 바이너리 포맷 파서는 Plan 단계에서 "검증용 실파일 출처와 라이선스"를 먼저 정한다
- 합성 바이트 테스트는 가능하면 실파일에서 뽑은 바이트를 그대로 쓴다
