## 1. 프로젝트 목적

**궁극 목표는 "그룹 전체에서 사용 가능한 Agent Builder 플랫폼"이다.**
상상인플러스저축은행 여신 부서는 최초 검증 무대(beachhead)이며, 확장 경로는
**여신 부서 → 전 부서 → 그룹 전체**다. 따라서 기능 설계 시 "여신에만 통하는 구조"와
"모든 부서에 일반화되는 구조"가 충돌하면 **일반화 쪽이 이긴다** (여신 특화는 KB·에이전트
구성 데이터로 담고, 플랫폼 코어에 하드코딩하지 않는다).

사내 실도입과 이직 포트폴리오 둘 다 목적이되, **사내 도입이 우선**이다 — 실사용 검증을
거친 결과물 자체가 포트폴리오의 서사가 된다.

금융 도메인 불변 원칙: **"근거 없으면 답하지 않는다(미근거 = 공란)"**,
**"LLM은 제안, 사람이 확정"**, **"모델은 고정, 데이터가 성장"**.

## 2. 페르소나

**주인공은 P2다.** 기능 우선순위가 충돌하면 P2(에이전트를 만들어 조직에 공급하는 사람)를
먼저 만족시킨다 — 플랫폼의 확장(전 부서 → 그룹)은 P2가 각 부서에서 에이전트를 직접
만들 수 있어야 성립하기 때문이다.

### P2. KB 운영자 / 에이전트 소유자 ★ 주인공
- **상황**: 부서 문서(PDF·엑셀 요율표)를 지식베이스에 적재하고, 에이전트를 구성해 부서에 배포.
- **원하는 것**: 업로드 → 청킹 확인 → 검색 품질 검증까지 **화면 안에서 폐루프**. DB/Swagger 직접 조작 없이.
- **플랫폼 관점**: 이 페르소나가 "개발자 없이" 에이전트를 만들 수 있는 정도가 곧 확장 가능성.
- 근거: kb-retrieval-test.plan("업로드→저장→검색 품질까지 KB 화면 안에서 폐루프 검증")

### P1. 여신 심사역 (beachhead 도메인의 대표 최종 사용자)
- **상황**: 심사 중 규정·조문 근거가 필요. 사내 용어("한도"="여신 한도")가 일반어와 다름.
- **원하는 것**: 빠른 답이 아니라 **출처를 신뢰할 수 있는 답**. 근거 조문 인용 선호.
- **AI 숙련도**: 낮음~중간. 프롬프트 작성 부담을 시스템이 대신 져야 함 (메모리 주입의 존재 이유).
- 근거: agent-memory.plan("심사팀 소속, 근거 조문 인용 선호"), kb-content-browser.plan("여신심사기준.pdf")

### P3. 관리자 (부서 관리자 / 시스템 관리자)
- **상황**: 조직 지식(org 메모리·위키 draft) 승인 큐 처리, 적재량·질문량·만족도 관제, 사용자/MCP 관리.
- **원하는 것**: 한 사용자의 오답이 전사 지식이 되지 않게 하는 **승인 게이트의 실질적 운영**.
- 근거: admin-dashboard.plan, agent-memory-org-scope.plan("부서 관리자 승인 게이트")

### P4. 일반 행원 (비기술 임직원)
- **상황**: 일상어로 질문("대출 한도 얼마까지 돼?"). 에이전트 내부 동작을 모름.
- **원하는 것**: 어려운 검색 없이 답 + **AI가 뭘 근거로 답했는지 눈으로 확인** (블랙박스 해소).
- 근거: agent-chat-reasoning-display.plan("비기술 임직원도 진행 상황을 이해 가능")

## 3. 핵심 시나리오

### S1. 지식베이스 구축·검증 폐루프 (P2) ★ 주인공 시나리오
KB 생성 → 문서 업로드(PDF/엑셀) → 청킹 전략 선택 → 콘텐츠 브라우저로 저장 상태 확인 →
리트리버 테스트로 실검색 검증 → 에이전트에 KB 연결 → 부서에 배포.
**성공 기준**: 이 전 과정에 DB/Swagger 직접 조작이 0회. 개발자 개입 없이 P2 혼자 완주 가능.

### S2. 규정 근거 확인 (P1 → 전 부서 일반화) — 신뢰성의 축
심사역이 사내 용어로 질문 → 메모리(소속·용어 선호) 자동 주입 → wiki-first + 라우팅 검색 →
근거 배지 달린 답변 → 원문 대조 → 틀렸으면 👎 + 이유 → 메모리·위키 draft로 환류.
**성공 기준**: 답의 속도가 아니라 "근거를 열어 확인했을 때 실제로 그 내용이 있는가".
(여신 규정은 예시일 뿐 — 인사 규정, 총무 지침 등 모든 부서 문서에 동일 구조 적용)

### S3. 정형 문서 작성 보조 (P1) — 문서 자동화의 축
양식 등록 → 채팅으로 슬롯 채움("ㅇㅇ상사 여신심의서, 여신금액 5억, oo문서 근거로 소견도") →
근거 있는 슬롯만 채워짐, **근거 없는 슬롯은 공란** → 미리보기 하이라이트로 확인 → 확정.
**성공 기준**: 환각 슬롯 0. 공란은 실패가 아니라 정직함.

### S4. 조직 지식 승인 (P3) — 거버넌스의 축
반복 👎(빈도 집계)·고평가 답변이 draft로 승격 대기 → 관리자가 출처(source_refs)를 열어 검증 →
승인 시에만 조직 전체에 노출.
**성공 기준**: 승인 없이 전사에 퍼진 자동 생성 지식 0건.

### S5. 업무 데이터 분석 (P1/P4)
여신 업무 데이터(요율표·한도표·여신 현황 엑셀) 업로드 → 분석 + 차트 → 재질문 시 원천
데이터 재사용.
**성공 기준**: 분석 결과의 수치가 원본 표에서 역추적 가능.
(주: 아카이브의 휴가/연차 예시는 개발 샘플 — 방향은 유효하나 실제 대상은 업무 데이터)

## 4. 명시적 비목표 (소유자 확정)

- **외부(대고객) 노출 없음** — 사내 임직원 전용. 대고객 챗봇·외부 API 제공은 스코프 밖.
- **자동 여신 의사결정 없음** — AI가 승인/거절을 결정하지 않는다. 항상 사람의 판단 보조까지만.

> 참고: "파인튜닝 없음", "무승인 자동 학습 없음"은 하드 비목표로 박제하지 않았다
> (미래에 바뀔 수 있는 항목). 다만 현재는 growing-agent-vision의 원칙 1·2가 동일 효과를 낸다.
