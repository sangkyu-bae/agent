# plain-tone — 공식 문서 어투 교정

프로젝트를 설명하는 글은 **한 일을 그대로 말하는 격식 있는 문장**으로 쓴다.
읽는 사람이 "실제로 무엇을 했는지"를 문장마다 알 수 있어야 하고,
멋있어 보이려고 고른 단어도, 회의 자리의 입말도 그 사실을 가리면 안 된다.

이 스킬은 문장 단위 어투만 다룬다. 무엇을 말할지는 `project-story`, 문서 구조는 `doc-writer`가 맡는다.
함께 쓸 때는 `project-story`로 내용을 고르고 `doc-writer`로 배치한 뒤 이 스킬로 문장을 손본다.

---

## 0. 적용 범위

| 적용한다 | 적용하지 않는다 |
|---------|---------------|
| README, 프로젝트 소개, 포트폴리오, 발표 원고 | 코드 주석, 커밋 메시지 |
| 자기소개서, 경력 기술서, 지원서 문항 | PDCA 계획·설계 문서 (내부 용어 사용이 전제) |
| 사내 도입 안내, 공지, 사용 가이드 | 위키 (`docs/wiki/`) — `/wiki` 명령으로만 수정 |
| 외부 공개용 기술 설명 글 | |

## 1. 네 가지 원칙

1. **통용되는 이름으로 부르고, 내부 조어는 풀어 쓴다.** 업계에서 바로 알아듣는 이름(할루시네이션 방지 모듈, 승인 게이트, MCP 레지스트리, 미들웨어)은 그대로 쓴다.
   프로젝트 안에서만 통하는 이름("응답봉투", "근거 판정 루프", "환류")은 **무엇이 무엇을 하는지**로 바꾼다.
2. **한 일의 크기만큼만 말한다.** 세 번 고쳤으면 "세 번 수정했다"이지 "진화시켰다"가 아니다.
   과장·비유 동사(진화, 고도화, 극대화, 쌓다, 못 박다)를 쓰지 않는다.
3. **격식 있는 문어체로 쓴다.** 공식 문서다. "붙는다", "끼운다", "돌린다", "죽는다", "찍는다" 같은 구어 동사를 쓰지 않는다.
   "연결된다", "추가한다", "실행한다", "중단된다", "생성한다"로 쓴다. 쉬운 말과 구어체는 다르다.
4. **글쓴이의 문장으로 쓴다.** 운율을 맞춘 대구, 반전을 노린 "~가 아니라 ~다", 문단 끝 교훈 한 줄,
   항목을 꼭 셋으로 맞추는 버릇은 글쓴이가 아니라 모델의 습관이다. 보이면 지운다.

## 2. 고칠 표현 여섯 갈래

자세한 목록과 대체어는 `references/phrases.md`에 있다. 여기서는 갈래와 판별 기준만 적는다.

### A. 내부 조어 · 번역투 명사
프로젝트 안에서만 통하는 이름, 영어 용어를 한자어로 옮긴 말.
"응답봉투", "환류", "표류", "결재함", "드릴다운", "역설계", "검증 무대", "넣은 장치".
→ 그 이름이 하는 일로 바꾼다. 꼭 써야 하면 처음 한 번 괄호로 풀어 쓴다.
→ **업계 통용어·표준 용어·고유명사는 조어가 아니다.** 할루시네이션, 승인 게이트, 미들웨어, MCP, RAG, BM25, RRF, Qdrant, LangGraph는
   개발자·관리자 독자에게 그대로 쓴다. 비전공자 독자라면 `doc-writer/references/glossary.md`를 따른다.
→ 기능을 부르는 이름은 `project-story` §3의 모듈 이름을 따른다.

### B. 과장 · 비유 동사
한 일보다 크게 들리는 동사, 비유로 쓴 동사.
"진화시켰다", "고도화했다", "쌓았다(네 겹으로)", "못 박았다", "끌어올렸다", "극대화했다", "혁신했다", "확보했다", "봉인했다".
→ 격식 있는 실제 행위 동사로 바꾼다. "세 번 다시 설계했다", "검색을 네 단계로 구성했다", "정했다", "높였다".
→ "구현했다", "적용했다", "도입했다", "설계했다"는 과장이 아니다. 격식체 동사로 그대로 쓴다.

### C. 모델 습관 문장
글쓴이가 의도하지 않았는데 들어가는 패턴. 하나라도 보이면 지운다.
- 대구·경구: "판단은 사람의 시간에, 집행은 시스템의 시간에"
- 반전 구조 반복: "장식이 아니라 게이트가 되도록", "성능이 아니라 신뢰의 문제"
- 문단 끝 한 줄 교훈·요약: "~한 것입니다.", "이것이 ~의 핵심이었습니다."
- 셋씩 묶기 습관: 근거 없이 항목을 꼭 세 개로 맞추는 것
- 명사 나열형 서술: "설계·구현·검증을 수행했습니다" → "설계하고 구현하고 검증했습니다"
- 군더더기 동사: "수행했다", "진행했다"가 다른 동사 뒤에 붙는 경우 → "개발을 진행했다"는 "개발했다"
- "~를 통해", "~를 기반으로", "~를 제공합니다", "~할 수 있습니다"의 반복
- 모든 항목 이모지, 문장 안 굵은 글씨 남발

### D. 모호어
수치나 동작으로 바꿀 수 없으면 지운다.
"다양한", "효율적으로", "원활한", "체계적으로", "안정적으로", "유연하게", "적절히", "상당히", "일정 수준", "전반적으로", "효과적으로", "강력한", "지능형", "차세대".
→ "다양한 도구" → "메일·문의 조회·일정 등록 도구". "안정적으로" → 무엇이 안 죽는지 쓰거나 삭제.

### E. 확인 안 된 사실 · 진행형
"운영 중입니다", "~로 나아가고 있습니다", "~를 지향합니다", "N% 절감".
→ 근거가 있을 때만 쓴다. 없으면 빼고 "확인 필요" 목록에 올린다.

### F. 구어체 · 가벼운 표현
공식 문서에 어울리지 않는 입말.
"붙는다/붙인다", "끼운다/끼워 넣는다", "돌린다/돌아간다", "죽는다/꺼진다", "찍는다", "걸어 둔다", "잡는다", "뚫린다", "걷어낸다",
"올린다(결재함에)", "뺀다", "고친다", "넘긴다", "쓴다(사용)", "본다(확인)".
→ "연결된다/추가된다", "구성한다", "실행한다/동작한다", "중단된다/장애가 발생한다", "기록한다", "등록한다", "검출한다", "우회된다", "제거한다",
   "등록한다/제출한다", "제외한다", "수정한다", "전달한다", "사용한다", "확인한다".
→ 종결은 "~한다/~된다/~입니다"로 통일한다. "~하자", "~잖아", "~거든" 같은 말투는 쓰지 않는다.

## 3. 바꾸는 요령

| 원래 문장 | 고친 문장 | 갈래 |
|-----------|-----------|------|
| 생성 방식을 세 번 진화시켰습니다. | 에이전트 생성 방식을 세 번 다시 설계했습니다. | B |
| 검색을 네 겹으로 쌓았습니다. | 검색을 네 단계로 구성했습니다. | B |
| 서버는 응답봉투에 담아 보냅니다. | 서버가 보내는 메시지는 종류·내용·시각을 담은 한 가지 형식으로 통일했습니다. | A |
| 판단은 사람의 시간에, 집행은 시스템의 시간에 하도록 분리했습니다. | 담당자가 승인하면 시스템이 지정한 시각에 실행합니다. | C |
| 설계 문서가 장식이 아니라 게이트가 되도록 한 것입니다. | 구현 후 설계와 코드를 대조해 맞지 않으면 완료로 인정하지 않았습니다. | C |
| 비목표로 못 박아 스코프 표류를 막았습니다. | 고객 직접 노출과 여신 자동 결정은 하지 않기로 정했습니다. | A, B |
| 피드백 환류 구조를 구축했습니다. | 👍/👎 평가를 다음 답변에 반영합니다. | A, B |
| 다양한 도구를 효율적으로 연동할 수 있습니다. | 메일, 문의 조회, 일정 등록 도구를 관리자 페이지에서 등록하면 에이전트가 사용합니다. | D |
| 외부 시스템은 등록만으로 붙습니다. | 외부 시스템은 관리자 페이지에서 등록하면 재배포 없이 연결됩니다. | F |
| 서버 하나가 죽어도 나머지 도구는 돌아갑니다. | 서버 하나에 장애가 생겨도 나머지 도구는 정상 동작합니다. | F |
| 초안을 결재함에 올립니다. | 초안을 승인 목록에 등록합니다. | A, F |
| 근거 판정 재작성 루프를 넣었습니다. | 할루시네이션 방지 모듈이 근거 없는 문장을 판정하고 재작성합니다. | A |
| PDCA 아카이브 43건을 역설계했습니다. | 지난 계획 문서를 다시 읽고 공통 요구를 정리했습니다. | A |
| 관측 체계를 고도화했습니다. | 질문 한 건마다 실행·단계·도구 호출·검색 근거를 기록합니다. | B, D |

고칠 때 지킬 것:
- **내용을 더하거나 빼지 않는다.** 문장이 모호해서 구체화할 사실을 모르면 추측해 채우지 말고 "확인 필요"로 남긴다.
- **수치는 그대로.** 반올림하거나 단위를 바꾸지 않는다.
- **문장당 한 가지.** 쉼표로 세 번 이상 이어지면 나눈다.
- **주어를 분명히.** 내가 한 일은 "저는/제가" 또는 생략, 시스템이 하는 일은 시스템을 주어로.
- **같은 뜻이면 짧은 쪽.** "~하는 것을 가능하게 했습니다" → "~하게 했습니다".
- **쉽게 쓰되 격식은 지킨다.** 전문 용어를 풀어 쓴다고 입말로 바꾸지 않는다.

## 4. 작업 절차

1. 대상 파일을 **끝까지 읽는다.** 일부만 읽고 고치지 않는다.
2. 독자를 확인한다. 인자에 없고 문서에서도 분명하지 않으면 사용자에게 묻는다.
   독자가 비전공자면 A 갈래에서 표준 용어도 `glossary.md`로 풀어 쓴다.
3. 문장마다 다섯 갈래(A~E)에 걸리는지 본다. 걸리는 문장을 **원문 → 고친 문장 → 갈래** 표로 먼저 정리한다.
4. 사용자가 `/plain-tone <파일>`로 직접 호출했으면 파일을 고치고, 다른 작업 중에 적용하는 것이면
   작성하는 문장에 규칙을 바로 적용한다.
5. 고친 뒤 §5 점검표를 돌린다.
6. 보고: 고친 문장 수, 갈래별 대표 사례 2~3개, "확인 필요" 목록. 파일 전체를 다시 붙이지 않는다.

## 5. 마지막 점검

```
□ 내부 조어·번역투 명사가 풀어 쓰이지 않고 남아 있는가 (A)
□ 한 일보다 크게 들리는 동사가 있는가 (B)
□ 대구·반전·문단 끝 교훈·셋 묶기가 있는가 (C)
□ "다양한·효율적으로·안정적으로" 같은 말이 수치나 동작 없이 남아 있는가 (D)
□ 근거 없는 사실·진행형 문장이 있는가 (E)
□ "붙는다·돌린다·죽는다·찍는다·걸어 둔다" 같은 구어 동사가 있는가 (F)
□ 공식 문서로 제출해도 어색하지 않은 격식체인가
□ 내용·수치가 원문과 같은가 (더하거나 빼지 않았는가)
□ 표준 용어·고유명사를 조어로 오인해 망가뜨리지 않았는가
```

## 6. 관련 스킬·문서

- `doc-writer` — 독자별 구조·내용 선택. 문체 규칙은 이 스킬을 따른다.
- `doc-writer/references/glossary.md` — 비전공자용 용어 대응표.
- `references/phrases.md` — 갈래별 금지 표현과 대체어 전체 목록.
