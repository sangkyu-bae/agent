# doc-writer — 독자 맞춤 문서 작성

같은 제품이라도 누가 읽느냐에 따라 앞에 둘 내용과 써도 되는 단어가 다르다.
이 스킬은 **독자를 먼저 정하고**, 그 독자가 30초 안에 "이게 뭐고 나한테 왜 필요한지"
말할 수 있게 쓰는 것을 목표로 한다.

---

## 0. 시작 절차

1. **독자 확인** — 인자에 독자가 없으면 AskUserQuestion으로 4종 중 하나를 묻는다. 추측하지 않는다.
2. **대상 확인** — 기존 파일을 다시 쓰는 것이면 먼저 전체를 읽는다. 새로 쓰는 것이면 저장 위치를 확인한다.
3. **사실 수집** — 기능·사례·수치는 코드와 문서에서 확인한 것만 쓴다.
   근거 위치: `docs/SOURCE-OF-TRUTH.md`(SOT가 오래됐으면 코드가 진실), `docs/USER-SCENARIOS.md`,
   `idt/db/migration/`, `idt/src/api/main.py`, `idt_front/src/pages/`.
4. **비전공자 여부 판단** — 아래 독자 표의 "비전공자" 열이 예이면 §3 용어 규칙을 반드시 적용한다.
5. 작성 → §5 점검 → 결과와 함께 "확인이 필요한 사실" 목록을 사용자에게 보고한다.

## 1. 독자별 작성 기준

| 독자 | 비전공자 | 먼저 보여줄 것 | 빼야 할 것 |
|------|---------|---------------|-----------|
| **채용 담당자·면접관** | 혼재 (인사 담당은 예, 기술 면접관은 아니오) | 해결한 문제, 실제 사례, 내 역할, 기술 판단과 그 이유, 결과 | 설치 절차 세부, 사내 개발 규칙 |
| **사내 경영진·타 부서** | 예 | 어떤 업무가 얼마나 줄어드는지, 실제 사례, 안전장치(사람 승인·근거 없으면 답하지 않음), 비용·위험 | 기술 스택, 코드 구조, 내부 구현 용어 |
| **사내 실무자** (에이전트를 만들고 쓰는 사람) | 예 | 화면 순서대로 따라 하는 방법, 무엇을 입력하면 무엇이 나오는지, 막혔을 때 할 일 | 아키텍처, DB, 내부 규칙 |
| **외부 개발자** | 아니오 | 무엇을 하는 프로젝트인지 한 줄, 실행 방법, 구조, 기여 방법 | 사내 조직 맥락, 내부 프로세스(PDCA 등) |

### 독자별 구조 템플릿

**채용 담당자·면접관**
```
한 줄 소개 (무엇을 해결하는 제품인가)
→ 실제 사례 2~3개 (무엇을 자동화했나)
→ 증거 (스크린샷/GIF, 수치)
→ 기술적으로 어려웠던 점과 판단 (왜 이렇게 설계했나)
→ 기술 스택 (짧게)
```

**사내 경영진·타 부서**
```
한 줄 소개 (어떤 일을 대신해 주나)
→ 우리 부서라면 이렇게 쓴다 (업무 사례)
→ 줄어드는 시간·일 (확인된 수치만)
→ 안전장치 (사람이 승인해야 실행됨, 근거 없으면 답하지 않음)
→ 도입하려면 무엇이 필요한가
```

**사내 실무자**
```
이걸로 무엇을 할 수 있나 (한 줄)
→ 따라 하기: 1단계, 2단계, 3단계 … (화면 이름·버튼 이름 그대로, 캡처 첨부)
→ 이럴 땐 이렇게 (자주 막히는 상황과 해결)
→ 문의처
```

**외부 개발자**
```
한 줄 소개
→ 데모 (스크린샷/GIF)
→ 주요 기능 (핵심 3~5개)
→ 빠른 시작 (복사해서 바로 실행되는 명령)
→ 구조 / 문서 링크 / 라이선스
```

## 2. 공통 문체 규칙

- **한 문장에 한 가지만.** 문장이 쉼표로 세 번 이상 이어지면 나눈다.
- **항목은 한 줄 설명.** "**이름**: 무엇을 하는지" 형태.
- **지금 되는 것만 쓴다.** "~로 나아가고 있습니다", "~를 지향합니다", "점점 ~할 예정" 같은 진행형·비전 문장 금지.
- **추상어 대신 사례.** "혁신적인", "지능형", "강력한", "성장하는", "차세대" 대신 실제로 하는 일을 쓴다.
  - ❌ "지능형 업무 자동화를 통해 생산성을 혁신합니다"
  - ✅ "매일 아침 홈페이지 문의를 읽고 답변 초안을 써 둡니다. 담당자는 확인 후 승인만 하면 됩니다."
- **확인 안 된 사실은 단정하지 않는다.** "운영 중", "N% 절감" 등은 근거가 있을 때만. 없으면 사용자에게 확인을 요청하고 문서에서는 뺀다.
- **AI 티 나는 표현 금지:** "~할 수 있습니다"의 반복, "다양한", "효율적으로", "원활한", "~를 제공합니다",
  문단 끝의 요약 반복, 모든 항목에 붙는 이모지.
- **프로젝트 표기:** 제품명은 "Agent Builder".

## 3. 비전공자 용어 규칙

비전공자 독자(위 표에서 "예")에게는 기술 용어를 그대로 쓰지 않는다.

1. **바꿀 수 있으면 일상어로 바꾼다.** `references/glossary.md`의 대응표를 쓴다.
2. **꼭 써야 하는 용어**(화면에 그 단어가 그대로 나오는 경우 등)는 처음 한 번만 괄호로 풀어 쓴다.
   - 예: "MCP(사내 시스템과 에이전트를 잇는 연결 통로)"
3. **약어는 쓰지 않는다.** RAG, LLM, API, KB, JWT, RBAC 등. 화면에 나오면 2번 규칙을 따른다.
4. **구조 대신 결과를 설명한다.** "벡터 검색과 키워드 검색을 결합한 하이브리드 검색" →
   "질문과 뜻이 비슷한 문서와 같은 단어가 들어간 문서를 함께 찾아옵니다".
5. **비유는 한 번만, 업무 비유로.** 에이전트 = "일을 맡길 수 있는 디지털 직원",
   승인 게이트 = "결재". 같은 문서에서 비유를 바꿔 가며 쓰지 않는다.
6. **숫자·설정값은 의미로 쓴다.** "토큰 캡 800" → "기억해 두는 정보는 짧게 유지됩니다".

용어집에 없는 용어를 만나면 같은 원칙으로 풀어 쓰고, 작업 끝에 "용어집에 추가할 후보"로 사용자에게 알린다.
용어집 수정은 사용자가 요청할 때만 한다.

---

## 4. 증거 넣기

- 주장 하나에 증거 하나. "실제로 일한다"고 쓰면 결과 화면(승인함의 답변 초안, 발송된 메일 등)을 붙인다.
- 스크린샷은 계정·이메일·고객 정보·사내 조직명이 보이지 않게 자른다.
- 이미지 위치는 `docs/assets/` (`docs/img/`는 gitignore 대상이라 GitHub에서 깨진다).

---

## 5. 마지막 점검

```
□ 독자를 정했고, 그 독자의 "먼저 보여줄 것"이 문서 앞쪽에 있는가
□ 그 독자의 "빼야 할 것"이 들어가 있지 않은가
□ 30초 테스트: 첫 화면만 읽고 무엇을 하는 제품인지 한 문장으로 말할 수 있는가
□ 비전공자 독자라면: 풀어 쓰지 않은 기술 용어·약어가 남아 있지 않은가
□ 진행형·비전 문장, 추상어, AI 티 나는 표현이 없는가
□ 모든 사실·수치에 근거가 있는가 (없으면 사용자 확인 목록에 올렸는가)
□ 링크가 실제로 동작하는가 (백틱으로 감싼 `[text](url)` 은 링크가 아니다)
□ 이미지에 개인정보가 보이지 않는가
```

보고할 때는 결과 문서 경로, 바꾼 핵심 포인트, 확인이 필요한 사실, 용어집 추가 후보를 짧게 정리한다.
