# project-story — 이 프로젝트를 설명할 때 말할 것과 뺄 것

세 스킬의 역할:

| 스킬 | 정하는 것 |
|------|----------|
| **`project-story`** | **이 프로젝트에 대해 무엇을 말하고 무엇을 빼는지** |
| `doc-writer` | 독자별 문서 구조, 앞에 둘 순서 |
| `plain-tone` | 문장 어투 (격식 문어체, 조어·과장·구어 금지) |

포트폴리오·전체 소개·관리자 안내 모두 셋을 같이 쓴다. `project-story`로 내용을 고르고, `doc-writer`로 배치하고, `plain-tone`으로 문장을 다듬는다.

---

## 1. 핵심 메시지

> 담당자가 업무를 설명하면 에이전트가 만들어지고, 에이전트는 **등록된 도구 중 필요한 것으로 라우팅해 실제 업무를 수행**한다.
> 도구를 추가하면 에이전트가 할 수 있는 일이 늘어난다.

- **도구 추가 + 라우팅이 핵심이다.** 사내 시스템 연결(MCP)은 도구의 한 종류일 뿐이며, 그것만 강조하지 않는다.
- 에이전트가 하는 일의 범위는 도구 목록이 정한다. 예를 전부 나열하지 말고, 범위가 넓다는 것을 보여 주는 대표 예 2~3개만 든다.
  - 메일 루틴 업무 (조회·분류·답장 초안·발송)
  - 웹 검색·스크래핑으로 자료를 모아 알림이나 보고서를 만드는 일
  - 지침에 따라 페이지를 열고 버튼을 눌러 특정 자료를 가져와 분석·문서를 만드는 일
  - 홈페이지 고객 문의 답변 초안
- "사내 시스템에 연결돼 일한다"로 요약하지 않는다. "도구를 사용해 업무를 수행한다"로 요약한다.
- 제품 표기는 **Agent Builder**. "RAG 플랫폼", "챗봇", "LLM 서비스"로 부르지 않는다.

**규정·지침의 표현**: 규정과 지침은 **에이전트마다** 연결된다 (에이전트별 지식베이스·지침). 부서 규정인 경우가 많지만
"부서 문서"로 고정해 쓰지 않는다. "에이전트에 연결된 규정·지침"으로 쓰고, 예를 들 때 "부서 규정"을 든다.

## 2. 쓰지 않는 것

| 쓰지 않는다 | 이유 |
|------------|------|
| 코드 줄 수, 테스트 줄 수, 파일 수 | 얼마나 많이 썼는지는 무엇을 해결했는지를 말해 주지 않는다 |
| PDCA 사이클 수, 아카이브 건수, 문서 수, Match Rate | 사내 작업 방식의 수치 |
| 커밋 수, PR 수, 테이블 수, 라우터 수, 화면 수 | 같은 이유 |
| 계층 위반 0건, 타입 힌트 100% 같은 코드 품질 수치 | 같은 이유 |
| 개발 기간을 성과처럼 쓰는 것 ("N개월 만에") | 시작 시점만 필요하면 쓴다 |
| **첫 적용 부서·확장 경로 문구** ("저축은행 여신 부서에서 처음 적용", "부서 문서와 연결 시스템만 바꾸면 다른 부서에서도") | 독자에게 필요 없는 배경. 금융 맥락은 기능 설명 안에서 자연스럽게 드러나게 한다 |
| **역할·구성 메타 블록** ("설계·개발 전담(1인)", "구성: FastAPI + React") | 표지·요약에서 뺀다. 역할은 자소서 본문에서 문장으로만, 스택은 맨 끝 스택 절에서만 |
| "넣은 장치", "장치" 라는 라벨 | 어색하다. "기능", "모듈", "해결 방법"으로 쓴다 |
| 고정 선택처럼 쓰는 설정값 | §4 참고 |

**써도 되는 수치**는 판단의 근거와 업무 결과다.
- 판단 근거: "판정 모델 후보 비교에서 gpt-4o-mini는 정상 문장 7건을 모두 오판했다"
- 업무 결과: "문의 N건에 답변 초안을 생성했다" (측정 기록이 있을 때만)

작업 방식(설계 문서 선행, 테스트 선행)은 "협업 방식" 문단에서 수치 없이 한두 문장으로만 쓴다.

## 3. 기능은 모듈 이름으로 짧게 설명한다

긴 서사 대신 **통용되는 이름 + 한두 문장**으로 쓴다. 이름은 업계에서 바로 알아듣는 말을 고른다.

| 모듈 이름 (이렇게 부른다) | 한 줄 설명 | 쓰지 않는 표현 |
|--------------------------|-----------|---------------|
| **할루시네이션 방지 모듈** | 초안과 답변에서 근거 없는 문장을 판정하고 재작성한다. 상한을 넘기면 해당 문장을 제외한다 | 근거 판정 재작성 루프 |
| **승인 게이트** | 메일 발송·답변 등록처럼 되돌릴 수 없는 작업은 승인 후에만 실행된다 | 결재함에 올린다 |
| **실행자 신원 전달** | 외부 시스템 호출마다 실행자의 신원을 서명 토큰으로 전달해 본인 범위의 데이터만 접근한다 | 신원 헤더를 실어 보낸다 |
| **프롬프트 인젝션 방어** | 입력을 규칙과 LLM 판정으로 검사하고, 차단된 입력은 이후 대화에서 제외한다 | 입력 검사, 가드 |
| **실행 추적** | 질문 한 건을 실행·단계·도구 호출·LLM 호출·검색 근거 단위로 기록한다 | 관측, 드릴다운 |
| **조직 지식 승인** | 반복된 피드백은 관리자 승인을 거쳐야 공용 지식이 된다 | 환류, 승격 |
| **자연어 에이전트 생성** | 업무 설명에서 필요한 도구와 설정을 추론하고, 부족한 정보는 질문한다 | 말로 만들기, 컴포저 |
| **MCP 레지스트리** | 관리자 페이지에서 MCP 서버를 등록하면 재배포 없이 도구가 추가된다 | 등록만으로 붙는다 |
| **스케줄러** | 정해진 시각에 에이전트를 자동 실행한다 | 걸어 둔다 |
| **하이브리드 검색** | 의미 검색과 키워드 검색을 결합하고 한국어 형태소를 반영한다 | 뜻 검색과 단어 검색을 합친다 |

설명이 더 필요하면 아래 세 칸만 쓴다. 라벨은 **문제 / 해결 / 효과**.

```
문제 : 실제로 겪은 일 ("문의 답변 초안에 근거 없는 대표번호가 반복 생성됐다")
해결 : 모듈 이름 + 동작 ("할루시네이션 방지 모듈이 초안을 판정하고 근거 없는 문장을 재작성한다")
효과 : 담당자 입장에서 달라진 점 ("근거 없는 문장은 승인 목록에 올라오지 않는다")
```

- 모듈 하나에 세 칸. "문제"가 비면 그 모듈은 뺀다.
- 설계 판단이 있었으면 "이유" 한 줄을 덧붙인다 ("고정 규칙은 맞는 값까지 제외하므로 맥락 판정을 택했다").
- 스택 이름은 설명 안에서 필요할 때만 쓰고, 별도 "기술 스택" 절은 맨 끝에 짧게.

## 4. 설정 가능한 것은 설정 가능하다고 쓴다

고정된 선택처럼 쓰면 사실과 다르다. 아래는 모두 화면에서 바꿀 수 있다.

| 항목 | 어디서 | 쓰는 법 |
|------|--------|--------|
| 에이전트가 쓰는 LLM 모델 | 에이전트 생성·수정 화면 | "모델은 에이전트별로 선택한다 (OpenAI · Anthropic · 사내 설치형)" |
| 할루시네이션 판정 모델 | 관리자 페이지 | "판정 모델은 관리자 페이지에서 설정한다. 기본값은 비교 결과를 근거로 정했다" |
| MCP 서버·도구 | 관리자 페이지 | "관리자 페이지에서 등록한다" |
| 임베딩 모델, 청킹 방식 | 관리자 페이지 · 지식베이스 설정 | "지식베이스별로 선택한다" |
| 미들웨어 조합 | 에이전트 설정 | "에이전트별로 조합한다" |
| 승인 필요 도구 | 에이전트 설정 | "도구별로 승인 필요 여부를 지정한다" |
| 스케줄 | 에이전트 설정 | "에이전트별로 복수 등록한다" |

❌ "판정 모델은 gpt-4o로 정했다" → ✅ "판정 모델은 관리자 페이지에서 설정한다. 기본값 gpt-4o는 후보 비교 결과로 정했다."

## 5. 근거 지도

소개 글에 넣을 모듈은 여기서 고른다. 독자에 따라 3~6개를 고르고, 전부 넣지 않는다. 근거 문서를 읽고 사실을 확인한 뒤 쓴다.

| 모듈 | 문제 | 효과 | 근거 |
|------|------|------|------|
| 할루시네이션 방지 모듈 | 답변 초안에 근거 없는 대표번호가 반복 생성 | 근거 없는 문장이 승인 목록에 오르지 않음 | `docs/wiki/backend/patterns/grounding-rewrite-loop.md`, 아카이브 `draft-grounding-check`, `idt/src/config.py` (초안 2회·답변 1회 상한) |
| 승인 게이트 | 되돌릴 수 없는 작업을 에이전트가 단독 실행 | 승인 후 즉시 또는 예약 시각에 1회 실행 | `docs/wiki/backend/patterns/approval-gate-run-contract.md`, `idt/src/application/approval/` |
| 실행자 신원 전달 | 메일함 선택권이 LLM·입력에 있으면 타인 메일함 접근 가능 | 실행자 본인 범위만 접근 | 아카이브 `mcp-identity-header` |
| 자연어 에이전트 생성 | 에이전트 생성 속도가 개발자 수에 종속 | 담당자가 직접 생성 | 아카이브 `nl-agent-composer`, `docs/wiki/backend/patterns/stateless-hitl-clarification.md`, `declared-slot-elicitation.md` |
| LLM 출력 신뢰 경계 | LLM이 없는 도구 이름·계산값 생성 | 계산 필드는 코드가 채우고 없는 도구는 코드가 제외 | `docs/wiki/backend/patterns/llm-output-trust-boundary.md` |
| 프롬프트 인젝션 방어 | 입력에 섞인 지시문으로 에이전트 조종 | 차단된 입력은 이후 대화에서 제외 | `docs/wiki/backend/patterns/prompt-injection-guard.md` |
| MCP 레지스트리 | 도구 추가마다 재배포 | 관리자 페이지 등록으로 도구 추가, 서버 일부 장애 시 나머지 도구는 정상 | 아카이브 `dynamic-mcp-registry`, `docs/wiki/backend/patterns/degradation-vs-failure-boundary.md` |
| 실행 추적 | 답변의 근거와 비용 발생 지점을 알 수 없음 | 건별로 단계·도구·비용·근거 확인 | 아카이브 `agent-run-observability`, `docs/wiki/backend/patterns/run-step-hierarchy-and-latency.md` |
| 조직 지식 승인 | 한 사람의 피드백이 전체 지식으로 확산 | 반복 확인된 피드백만 승인 목록 상위, 승인 후 공용 | 아카이브 `recurring-feedback-promotion`, `wiki-feedback-loop` |
| 하이브리드 검색·조항 청킹 | 한국어 규정에서 조문 단위 검색 실패 | 해당 조항을 근거로 답변 | 아카이브 `clause-aware-chunking`, `kb-custom-chunking` |
| 검색 평가 | 검색 품질을 감으로 판단 | 설정 변경 전후를 수치로 비교 | 아카이브 `eval-feedback-loop` |
| 스케줄러 | 근무 시간 외에는 업무 중단 | 정해진 시각에 자동 실행 | 아카이브 `agent-schedule` (once/daily/weekly/cron, 외부 트리거) |

아카이브 위치: `idt/docs/archive/<YYYY-MM>/<기능명>/`. 지도에 없는 내용은 같은 형식으로 근거를 먼저 찾는다.

## 6. 에이전트가 실제 업무를 수행한다는 것을 앞세우는 법

1. **업무 사례로 시작한다.** 첫 화면에는 기능 목록이 아니라 담당자의 업무가 바뀌는 장면이 나온다.
2. **주어를 담당자로 둔다.** "시스템이 초안을 생성한다" 대신 "담당자는 승인 목록에서 초안을 확인하고 승인한다".
3. **도구 추가 → 라우팅 → 수행** 순서로 설명한다. "메일 도구를 추가하면 에이전트가 메일 업무를 수행한다. 스크래핑 도구를 추가하면 자료 수집과 보고서 작성을 수행한다."
4. **모듈은 실무 부서의 우려에 대한 답으로 꺼낸다.** 우려(잘못된 답, 지어낸 내용, 타인 정보, 근거 불명, 피드백 확산)를 먼저 쓰고 §3의 모듈을 답으로 붙인다.
5. **만드는 과정도 업무로 쓴다.** "'매일 아침 문의를 확인해 답변 초안을 작성하고 승인 후 등록'이라고 입력하면 필요한 도구가 선택된다".
6. **하지 않는 것도 쓴다.** 고객 직접 노출 없음, 여신 승인·거절 자동 결정 없음.

## 7. 문서 유형별 뼈대

**포트폴리오 / 자소서 (채용)**
```
1. 핵심 메시지 한 줄 (§1)
2. 업무 사례 1~2개
3. 실무 부서의 우려 → 모듈 (3~6개, §3 세 칸)
4. 설계 판단과 이유 1~3개
5. 협업 방식 (수치 없이)
6. 기술 스택 (짧게, 맨 끝)
```

**전체 소개 (경영진·타 부서)**
```
1. 핵심 메시지 한 줄
2. 이렇게 씁니다 (업무 사례 2~3개, 담당자 주어)
3. 만드는 방법 (자연어 입력 → 도구 선택 → 저장)
4. 안전장치 (우려 → 모듈, 표)
5. 비용·모델 선택·남은 위험
6. 도입에 필요한 것
```

**관리자 안내 (실무자·관리자)**
```
1. 관리자 페이지에서 할 수 있는 것 한 줄
2. 설정 항목별: 어디서 · 무엇을 · 기본값 · 바꾸면 무엇이 달라지는지 (§4 표 순서)
3. 도구(MCP) 등록 절차
4. 승인 목록 처리 절차
5. 실행 추적·비용 확인 방법
6. 이럴 땐 이렇게
```

---

## 8. 절차

1. 독자를 확인한다. 없으면 묻는다.
2. 대상 파일이 있으면 끝까지 읽고, §2에 걸리는 수치·문구·라벨을 표시한다.
3. §5 지도에서 독자에게 맞는 모듈을 고르고 근거 문서를 읽어 사실을 확인한다.
4. §3 형식(모듈 이름 + 한두 문장, 필요하면 문제/해결/효과)으로 쓴다. §4의 설정 가능 항목은 고정 선택처럼 쓰지 않는다.
5. `doc-writer`로 배치하고 `plain-tone`으로 문장을 다듬는다.
6. §9 점검표를 돌리고 "확인 필요" 목록과 함께 보고한다.

## 9. 마지막 점검

```
□ 핵심 메시지가 "도구 추가 → 라우팅 → 실제 업무 수행"인가 (사내 시스템 연결만 강조하지 않았는가)
□ 첫 화면이 업무 사례로 시작하는가
□ 코드 줄 수·테스트 줄 수·PDCA·Match Rate·커밋 수·품질 수치가 없는가
□ 첫 적용 부서·확장 경로 문구, 역할·구성 메타 블록이 없는가
□ "넣은 장치", "장치" 라벨이 없는가 (기능·모듈·해결)
□ 모듈이 통용되는 이름으로 불리는가 (할루시네이션 방지 모듈, 승인 게이트, MCP 레지스트리 …)
□ 설정 가능한 항목(모델·판정 모델·MCP·청킹·미들웨어·승인 도구·스케줄)을 고정 선택처럼 쓰지 않았는가
□ 규정·지침을 "에이전트에 연결된" 것으로 썼는가 (부서 문서로 고정하지 않았는가)
□ 제품을 Agent Builder로 부르고, RAG·챗봇을 제품명처럼 쓰지 않았는가
□ 하지 않는 것(비목표)이 한 줄 있는가
□ 모든 사실에 §5 근거 또는 코드 근거가 있는가
```
